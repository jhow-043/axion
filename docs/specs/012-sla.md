# P12 — SLA (Políticas, Motor e Jobs)

## Objetivo

Controlar os dois SLAs independentes de cada chamado — **SLA de Atendimento** (tempo para o técnico assumir) e **SLA de Resolução** (tempo para resolver) — com políticas totalmente configuráveis pelo admin, pausa automática em Pendente e jobs Celery para alertas e marcação de vencimento.

## Escopo

- `sla_policies`: definição de prazos por (tipo de chamado × prioridade × [equipe opcional]).
- `sla_trackers`: registro individual do SLA de cada chamado com estado, prazos e acumulador de pausa.
- Motor de SLA: cálculo de `attendance_due_at` e `resolution_due_at`; pausa e retomada do SLA de Resolução em Pendente.
- Jobs Celery Beat: varredura periódica de trackers ativos para:
  - Alertar quando o SLA está "em risco" (ex.: 80% do prazo esgotado).
  - Marcar como `breached` quando o prazo vence.
- API de leitura do SLA de um chamado.
- API de configuração de políticas (admin).
- Indicadores de SLA na tela de detalhe do chamado.

## Fora do Escopo

- Envio das notificações em si (P14 processa; P12 apenas dispara o gatilho).
- Horário comercial, feriados e pausas personalizadas (registrar como evolução v2).
- SLA por categoria (apenas tipo + prioridade + equipe no escopo atual).
- Relatórios de SLA (P16).

## Dependências

- **P01** (Multi-Tenancy).
- **P04** (Usuários e Permissões) — `require_permission("admin:config")`.
- **P07** (Catálogos) — prioridades e tipos de chamado são a base das políticas.
- **P09** (Chamados) — eventos de transição disparam a lógica de SLA:
  - Criação do chamado → inicia `sla_tracker` com `attendance_due_at`.
  - Assumido (`assigned_at`) → encerra SLA de Atendimento; inicia SLA de Resolução.
  - Pendente → pausa SLA de Resolução.
  - Em Atendimento (retomada de Pendente) → retoma SLA de Resolução.
  - Solucionado → encerra SLA de Resolução.
- **P14** (Notificações) — P12 chama `notification_service.notify()` para alertas de SLA.

## Regras de Negócio

### Seleção de Política

A política aplicada ao chamado é a mais específica disponível, nesta ordem de prioridade:
1. Política para `ticket_type + priority_id + team_id` (mais específica).
2. Política para `ticket_type + priority_id + team_id=null`.
3. Política para `ticket_type='all' + priority_id + team_id=null`.
4. Se nenhuma encontrada: nenhum SLA aplicado (tracker não criado; registrar aviso de configuração).

### SLA de Atendimento
- **Início:** criação do chamado (`created_at`).
- **Prazo:** `created_at + attendance_minutes`.
- **Encerramento:** quando o chamado é assumido (`assigned_at`).
  - `assigned_at ≤ attendance_due_at` → `attendance_status = 'met'`.
  - `assigned_at > attendance_due_at` (ou job detecta vencimento) → `attendance_status = 'breached'`.
- Após encerramento, o SLA de Atendimento não muda mais.

### SLA de Resolução
- **Início:** momento em que o chamado é assumido (`assigned_at`).
- **Prazo:** `assigned_at + resolution_minutes - total_paused_minutes` (recalculado a cada retomada).
- **Pausa:** ao entrar em `pending`:
  - Cria registro em `sla_pauses` com `paused_at = now()`.
  - `resolution_status = 'paused'`.
- **Retomada:** ao sair de `pending` para `in_progress`:
  - Fecha o registro de pausa (`resumed_at = now()`, `minutes = elapsed`).
  - Acumula `total_paused_minutes`.
  - Recalcula `resolution_due_at = original_resolution_due + accumulated_pause_minutes`.
  - `resolution_status = 'running'`.
- **Encerramento:** `resolved_at` preenchido em P09 → `resolution_status = 'met'` ou `'breached'`.

### Jobs Celery Beat

**Job de Alerta (frequência: a cada 5 minutos):**
Varre `sla_trackers` com status `running`; para cada um, calcula o percentual de tempo decorrido. Se `elapsed_pct ≥ alert_threshold_pct` e `*_alert_sent = false`:
- Dispara notificação (P14).
- Seta `*_alert_sent = true`.

**Job de Vencimento (frequência: a cada 5 minutos):**
Varre `sla_trackers` com status `running` e `*_due_at < now()`:
- Marca `*_status = 'breached'`.
- Registra evento de timeline (P10): `sla_attendance_breached` ou `sla_resolution_breached`.
- Dispara notificação (P14).

Ambos os jobs devem ser **idempotentes**: rodar duas vezes no mesmo chamado não duplica alertas ou eventos.

## Critérios de Aceite

- [ ] Criar chamado com política aplicável → `sla_tracker` criado com `attendance_due_at` correto.
- [ ] Assumir chamado → `attendance_status = 'met'` ou `'breached'` conforme o tempo; `resolution_due_at` calculado.
- [ ] Colocar em Pendente → `sla_pauses` criado; `resolution_status = 'paused'`.
- [ ] Retomar de Pendente → pausa fechada; `total_paused_minutes` acumulado; `resolution_due_at` recalculado.
- [ ] Job de vencimento marca `breached` quando prazo passa.
- [ ] Job de alerta dispara notificação na primeira vez que o limiar é atingido (não duplica).
- [ ] Admin cria política → novos chamados usam a nova política.
- [ ] `GET /tickets/{id}/sla` retorna dados corretos de ambos os SLAs.
- [ ] Chamado sem política aplicável → tracker não criado; sem erros.

## Estratégia de Testes

### Testes Unitários

- Seleção de política: dada uma combinação de tipo/prioridade/equipe, a política mais específica é selecionada.
- Cálculo de `attendance_due_at` e `resolution_due_at`.
- Cálculo de tempo restante com pausas acumuladas.
- Lógica de alerta: `elapsed_pct ≥ threshold` → alerta; `< threshold` → não alerta.
- Idempotência do job: tracker já `breached` → job não modifica.

### Testes de Integração

- Criar chamado → tracker com prazo correto.
- Assumir chamado → encerra attendance; inicia resolution.
- Pendente → pausa registrada; resolution pausada.
- Retomar → pausa fechada; prazo recalculado corretamente.
- Job de vencimento: forçar `*_due_at` no passado → tracker marcado `breached` + notificação disparada.
- Job de alerta: forçar `elapsed_pct ≥ threshold` → `alert_sent = true` + notificação disparada.

### Testes E2E

- Abrir chamado → detalhe exibe SLA de Atendimento em andamento.
- Assumir → SLA de Atendimento exibido como "Cumprido" ou "Vencido"; SLA de Resolução inicia.
- Colocar em Pendente → barra do SLA de Resolução congelada.
- Retomar → barra retoma com prazo estendido.
- Forçar vencimento → badge de SLA exibido como "Vencido".

## Riscos Técnicos

- **Precisão temporal e fuso horário:** todos os cálculos devem usar UTC; conversão para o fuso do tenant apenas na exibição.
- **Concorrência job × transição:** se uma transição acontece ao mesmo tempo que o job de vencimento, o tracker pode ser atualizado duas vezes. Usar `SELECT FOR UPDATE` ou verificação de pré-condição (`status = 'running'` antes de atualizar).
- **Propagação de tenant para tasks Celery:** o job varre todos os tenants; deve passar `tenant_id` explicitamente ao processar cada tracker (conforme convenção de P01).
- **Reprocessamento:** se o worker cair e o job rodar atrasado, não deve duplicar alertas ou eventos. Flags `alert_sent` e verificação de `status` garantem idempotência.

## Complexidade

**Alta** — cálculo temporal com pausas, dois SLAs independentes, múltiplos jobs e integração com P09, P10 e P14.
